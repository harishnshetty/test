#### [00:10:16 → 00:14:40] Caching Strategies and Choice of EKS over ECS

- For caching **database components** that update infrequently:
  - NoSQL: Use **DynamoDB Global Tables** (fully managed, multi-region replication).
  - SQL (MySQL/Postgres): Use **RDS replicas across regions** for near-real-time reads.
  - Use **ElasticCache (Redis/Memcached)** to cache frequent queries but avoid caching very old data to control costs.
- Difference between **EKS and ECS**:
  - ECS is simpler, suitable for small apps or batch jobs; abstracts container orchestration.
  - EKS offers **more control, customizability, and multi-region deployment capability**, which is critical for global e-commerce with low latency.
  - EKS supports hybrid setups (on-prem + cloud), centralized control, and better scaling management.

#### [00:16:14 → 00:20:38] Disaster Recovery (DR) and Business-Cost Tradeoffs

- Disaster recovery depends on **business criticality** and **cost tolerance**:
  - **Low cost / data loss acceptable**: Spin up new infrastructure after failure (cold DR).
  - **Moderate criticality**: Use multi-region services like DynamoDB Global Tables, multi-region Kubernetes clusters with autoscaling (warm DR).
  - **Highly critical**: Maintain fully warmed replicas of entire infrastructure in standby regions; immediate failover via Route 53 health checks.
- E-commerce example:
  - Critical services (order creation, payments) use **warm replicas**.
  - Less critical services (reviews, feedback) use **cold DR** to reduce costs.
- Data backup frequency: hourly/daily backups on S3 with cross-region replication.

#### [00:21:18 → 00:29:04] CI/CD Pipeline Design and GitOps Approach

- CI/CD tool choice depends on existing code repository and customer preference:
  - Code on **GitHub** → GitHub Actions.
  - Code on **GitLab** → GitLab CI/CD.
  - Code on **AWS CodeCommit** → AWS CodePipeline.
- Hershel’s experience mostly with GitHub Actions, GitLab CI/CD, and AWS CodePipeline.
- Pipeline stages for e-commerce microservices (monorepo assumed):
  1. **Linting and syntax validation**.
  2. **Unit testing** or Terraform validation.
  3. **Containerization:** Build Docker images and push to **AWS ECR**.
  4. **Deployment:** Trigger Argo CD/GitOps to deploy updated container images to Kubernetes.
  5. Optional **manual approval** for critical infrastructure changes (Terraform apply).
- Use **Terraform remote state in S3 with DynamoDB for locking**.
- Secure pipeline credentials with **AWS IAM roles and GitLab secrets management**.
- Benefits of GitOps (Argo CD + Helm):
  - Declarative infrastructure and app deployment.
  - Environment-specific customization without code repetition.
  - Faster recovery from failures by redeploying from code.

#### [00:38:08 → 00:45:57] Challenging Kubernetes Upgrade Experience

- Hershel describes upgrading **eight Kubernetes clusters** with 10 nodes each, ~50-60 pods per node, with minimal downtime.
- Challenges:
  - Kubernetes control plane must be upgraded **version by version**; node groups can jump versions.
  - Control plane supports only node groups up to two versions behind.
- Strategy:
  - Upgrade control plane first.
  - Add new node groups with the target version.
  - Migrate pods gradually using **node taints and pod draining**.
  - Rolling upgrade with traffic split between old and new nodes to avoid downtime.
- Automation of upgrade process after initial manual run.
- Rollback plan:
  - Full backups and Helm charts synchronized with cluster state.
  - Ability to restore cluster from backup or redeploy from code.
- Team size: 2-3 people.

#### [00:50:18 → 00:54:21] Cost Optimization in Healthcare Cloud Environments

- Healthcare/financial sectors prioritize **compliance, security, data retention, and encryption**.
- For mandated 30% cost reduction in an existing cloud setup, Hershel suggests:
  - Analyze **cost drivers** using AWS Trusted Advisor.
  - Use **Reserved Instances** for stable workloads, **Spot Instances** for non-critical workloads.
  - Reduce backup retention periods.
  - Clean up unused resources (old log groups, unattached volumes).
  - Conduct **AWS Well-Architected Framework reviews** for optimization.
- Hershel cautions that aggressive cost cutting risks impacting availability.

#### [00:54:59 → 01:01:36] Infrastructure as Code (IaC) Drift and Manual Changes

- IaC brings powerful automation but **configuration drift is a major challenge**.
- Drift usually happens when manual changes are made outside Terraform.
- Solutions:
  - Restrict manual access unless justified and time-limited.
  - Use Terraform commands like **terraform import** to sync state.
  - Delete and recreate resources if needed.
  - Version control Terraform code to track changes.
- In urgent production fixes requiring manual changes:
  - Prefer Terraform changes first.
  - If manual changes are necessary, **log, communicate, and backport those changes into IaC** ASAP.
- Hershel strongly advocates **avoiding manual cloud changes**.
---

#### [01:02:15 → 01:10:00] Terraform Directory Structure and Team Collaboration

- For multi-account AWS environments (e.g., UAT, prod, security, logging accounts):
  - Maintain a **dedicated Terraform repo for AWS organization setup**.
  - Group accounts by function (logging, security, networking, application).
- Terraform repo structure options:
  - Monorepo with folders per app.
  - Separate repos per microservice.
- Use **Terraform workspaces** to manage concurrent development by multiple engineers on the same environment.
- Workspaces create separate state files to avoid conflicts.
- Merge requests trigger pipelines that create and destroy workspaces after testing.
- Best practice: Promote changes from dev → UAT → prod without code changes, only variable updates.

- Hershel views AI tools as **assistive rather than replacement**:
  - AI can reduce time spent on repetitive tasks (e.g., debugging CI/CD failures).
  - AI outputs depend on **prompt quality and existing expertise**.
- Future trends:
  - AI agents integrated with pipelines for auto-troubleshooting.
  - Automated pod health monitoring and self-healing.
  - Potential reduction in headcount but increased demand for highly skilled engineers.
- Hershel is cautious about granting AI tools full write access to critical infrastructure, prefers read-only for now.
- Optimistic about AI coexistence and continuous learning.

### Key Insights

- **Global, low-latency architectures require multi-region deployment of compute and data layers (EKS + DynamoDB Global Tables).**
- **Kubernetes (EKS) preferred over ECS for complex, large-scale, multi-region microservices due to greater control and scalability.**
- **Disaster recovery design must balance business criticality and cost, with tiered approaches (cold, warm, hot DR).**
- **CI/CD pipelines integrated with GitOps tools (Argo CD, Helm) enable declarative, reliable, and auditable deployments.**
- **Strong emphasis on security, monitoring, and compliance, especially in healthcare and financial sectors.**
- **Terraform workspaces and remote state management are key to enabling multiple engineers to collaborate safely.**
- **Manual changes in cloud environments cause drift and must be minimized with strict access controls and processes.**
- **AI/ML tools will augment DevOps efficiency but require skilled human oversight for safe adoption.**

| EKS                | Amazon Elastic Kubernetes Service - managed Kubernetes service                                |

| CloudWatch         | AWS monitoring and logging service                                                            |
| CloudTrail         | AWS service for logging API calls and user activity                                           |
| VPC Flow Logs      | Capture IP traffic going to and from network interfaces in a VPC                              |
