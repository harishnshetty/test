what is k8s 
**Kubernetes (K8s)** is an **open-source container orchestration platform** used to **automate deployment, scaling, and management of containerized applications**.


👉 In short: It helps run and manage containers (like Docker) across multiple servers efficiently.


what is eksctl
**eksctl** is a **command-line tool** used to **create and manage Amazon EKS (Elastic Kubernetes Service) clusters** easily.

👉 In short: It’s the **simplest way to create, configure, and delete EKS clusters** using a single command.



k8s artcthirure and explain
**Kubernetes Architecture** has **two main parts**:

1. **Control Plane (Master Node)** – manages the cluster.

   * **API Server** – entry point for all commands.
   * **etcd** – stores cluster data (key-value store).
   * **Controller Manager** – maintains desired state.
   * **Scheduler** – assigns pods to nodes.

2. **Worker Nodes** – run applications.

   * **Kubelet** – communicates with the control plane.
   * **Kube Proxy** – manages networking and load balancing.
   * **Container Runtime** – runs containers (e.g., Docker, containerd).

👉 In short: **Control Plane manages**, and **Worker Nodes run** the workloads.

What is a Pod in Kubernetes and what is it used for?

A Pod in Kubernetes is the smallest and simplest unit
in the cluster, representing a single instance of a
running process. Pods are used to host the containers
that run the applications and services in the cluster.
Pods provide a way to manage the deployment and
execution of containers in the cluster, making it easier
to manage the scaling, placement, and lifecycle of the
containers.

what is ingress controller
**Ingress Controller** is a **Kubernetes component** that manages **external HTTP/HTTPS access** to services inside the cluster.

👉 It works with **Ingress resources** to route traffic (like `/app1`, `/app2`) to the right services.

**Example:**

* You expose multiple apps through **one public IP** using an **Ingress Controller** (like NGINX or AWS ALB).


kubernets servcies list
Kubernetes has **4 main types of Services**:

1. **ClusterIP** – default; exposes service **inside the cluster only**.
2. **NodePort** – exposes service on a **port of each node** (accessible externally via `<NodeIP>:<Port>`).
3. **LoadBalancer** – exposes service **externally using a cloud load balancer**.
4. **ExternalName** – maps service to an **external DNS name**.

👉 In short:
`ClusterIP` (internal) → `NodePort` (basic external) → `LoadBalancer` (cloud external) → `ExternalName` (DNS mapping).


deployment staegry
Kubernetes **deployment strategies** define **how updates are rolled out** to pods. Common ones are:

1. **Recreate** – stop old pods first, then start new ones (downtime).
2. **Rolling Update** *(default)* – gradually replace old pods with new ones (zero downtime).
3. **Blue-Green** – two environments; switch traffic from old (blue) to new (green).
4. **Canary** – release new version to a small % of users, then increase gradually.

👉 In short: Use **Rolling Update** for production; **Blue-Green/Canary** for safer gradual rollouts.


replication controller
**Replication Controller (RC)** ensures that a **specified number of pod replicas** are always running in a Kubernetes cluster.

👉 If a pod fails or is deleted, RC automatically **creates a new one** to maintain the desired count.

**Example:**
If desired replicas = 3 and 1 pod crashes → RC creates a new one.

*(Note: RC is older; now replaced by **ReplicaSet**.)*

* **ReadWriteOnce (RWO):** One node can **read/write**. *(e.g., AWS EBS)*

What is a Persistent Volume (PV) and a Persistent Volume
Claim (PVC) in Kubernetes and what are they used for?

A Persistent Volume (PV) in Kubernetes is a resource that
represents a piece of storage in a cluster. It is used to provide
persistent storage for pods, and it can be backed by local
storage, network-attached storage, or cloud storage. A
Persistent Volume Claim (PVC) in Rubernetes is a request for
storage made by a pod, and it is used to claim a PV and
mount it as a volume in the pod. PVCs and PVs are used
together to provide persistent storage for stateful
applications in a cluster.


How does Kubernetes manage storage for containers?

Kubernetes manages storage for containers using
Persistent Volumes (PVs) and Persistent Volume
Claims (PVCs). PVs represent a piece of storage in a
cluster, and PVCs are requests for storage made by
pods. Pods use PVCs to claim PVs and mount them
as volumes in the pod, providing persistent storage
for containers.


What is a PersistentVolume in Kubernetes and what is it used
for?

A PersistentVolume in Kubernetes is a resource that
represents a piece of storage in the cluster that can
be dynamically provisioned
provisioned. PersistentVolumes are used to provide
storage for pods that requires persistence across
pod restarts and failures.


sidecar container
A **Sidecar Container** is a **secondary container** that runs alongside the **main application container** in the same Pod.

It helps by adding **supporting features** like:

* Logging/monitoring (e.g., Fluentd)
* Proxying (e.g., Envoy, Istio)
* Data sync or backup tasks

👉 In short: **Sidecar = helper container** that extends or supports the main app in a Pod.


taint [node ]and toleration [pod]
**Taint (Node):** Used to **repel pods** from a node unless they tolerate it.
**Toleration (Pod):** Allows a **pod to be scheduled** on a tainted node.

👉 In short:

* **Taint = “Keep pods away unless allowed.”**
* **Toleration = “I can handle this taint, place me here.”**

**Example:**

```bash
kubectl taint nodes node1 key=value:NoSchedule
```

Only pods with a matching toleration can run on `node1`.


**Node Affinity** – defines **rules for scheduling pods** on specific nodes based on labels.

**Taint Effects:**

* **NoSchedule** → Pod **won’t be scheduled** on the node.
* **PreferNoSchedule** → Tries **to avoid** scheduling, but not guaranteed.
* **NoExecute** → **Evicts existing pods** and **prevents new ones** unless they tolerate the taint.

👉 In short:

* **NoSchedule** = don’t place new pods.
* **PreferNoSchedule** = avoid if possible.
* **NoExecute** = kick out and block pods.


rbac 
**RBAC (Role-Based Access Control)** controls **who can do what** in a Kubernetes cluster.

It uses:

* **Role / ClusterRole** → defines permissions.
* **RoleBinding / ClusterRoleBinding** → assigns those permissions to users, groups, or service accounts.

👉 In short: RBAC = **secure access control** → “who can access which resources and actions.”



what is hpa and vpa

**HPA (Horizontal Pod Autoscaler):**
Automatically **scales the number of pods** based on CPU, memory, or custom metrics.
👉 Example: Add more pods when CPU > 80%.

**VPA (Vertical Pod Autoscaler):**
Automatically **adjusts CPU and memory limits/requests** of existing pods.
👉 Example: Give more RAM to a heavy pod instead of adding new ones.

**In short:**

* **HPA → scales out/in (more or fewer pods)**
* **VPA → scales up/down (bigger or smaller pods)**

What is a Horizontal Pod Autoscaler (HPA) in Kubernetes and
what is its purpose?

The Horizontal Pod Autoscaler (HPA) in Kubernetes is a built-
in tool that automatically adjusts the number of replicas of a
deployment, based on observed CPU utilization or other
custom metrics. The purpose of HPA is to ensure that a
deployment has enough resources to handle incoming traffic,
and it helps to maintain the desired performance levels of a
deployment.


network policy [ingress and egress]
**Network Policy** in Kubernetes controls **how pods communicate** with each other and with external endpoints.

It defines **rules for ingress (incoming)** and **egress (outgoing)** traffic based on **labels**, **namespaces**, and **ports**.

👉 In short: NetworkPolicy = **firewall for pods** — allows or blocks traffic between them.

What is a network policy in Kubernetes and what is it used
for?

A network policy in Kubernetes is a resource that defines the
allowed ingress and egress traffic to pods in the cluster.
Network policies are used to control the communication
between pods, and to limit the exposure of pods to the
network. Network policies provide a way to enforce security
and isolation between pods, ensuring that only authorized
traffic is allowed to reach the pods.

**1. Deployment** – Manages **stateless applications**.

* Ensures desired replicas of pods.
* Supports rolling updates and rollbacks.
  👉 Example: Web servers, APIs.

A cluster administrator needs to provide stable IP addresses
for a group of stateful pods in the cluster. What type of
Service should the administrator use to accomplish this?

A Headless Service should be used to provide stable IP
addresses for a group of stateful pods. Headless
Services do not provide a stable IP address for the
Service as a whole, but instead provide stable IP
addresses for each individual pod that is part of the
Service. This makes it easy to provide stable IP
addresses for stateful pods, which can be used for
communication between pods.

**2. StatefulSet** – Manages **stateful applications**.

What is a StatefulSet in Kubernetes?
A StatefulSet is a Kubernetes object that manages stateful applications, such as databases, message brokers, and other stateful applications that require persistent storage. Unlike a Deployment, a StatefulSet provides stable network identities, persistent storage, and guarantees the order of deployment and scaling.

* Each pod has a **unique identity** and **persistent storage**.
  👉 Example: Databases (MySQL, MongoDB).

What is a Job in Kubernetes and what is it used for?

A Job in Kubernetes is a resource that runs a specified
number of pods to completion, ensuring that the specified
number of successful completions is achieved. Jobs are used
to run batch jobs, such as data processing and image
rendering, in the cluster. Jobs provide a way to run batch jobs
in the cluster, ensuring that the batch job is run to
completion and that the specified number of successful
completions is achieved.

**3. DaemonSet** – Runs **one pod on every node** (or selected nodes).

What is a DaemonSet in Kubernetes?

A DaemonSet is a Kubernetes object that ensures a
single instance of a pod is running on each node in
a cluster. This is useful for deploying system-level
services, such as log collectors, node-level
monitoring agents, and other utilities that need to
run on every node.

* Used for background agents or monitoring tools.
  👉 Example: Log collectors, node exporters.

**In short:**
`Deployment → stateless` | `StatefulSet → stateful` | `DaemonSet → per node`.

What is a CronJob in Kubernetes and what is it used for?

A CronJob in Kubernetes is a resource that runs a
specified job on a schedule, using a cron
expression. CronJobs are used to run jobs, such as
backups and system maintenance, on a schedule in
the cluster. CronJobs provide a way to run jobs on a
schedule in the cluster, ensuring that the jobs are
run automatically at the specified times.

A Secret in Kubernetes is a resource that stores

store sensitive information that is needed by the

credentials and APT keys. Secrets provide a way to

by the pods that need it.

What is a ConfigMap in Kubernetes and what is it used for?

A ConfigMap in Kubernetes is a resource that stores
configuration data as key-value pairs. ConfigMaps are
used to store configuration data, such as command line
arguments, environment variables, and configuration
files, that are needed by the applications running in the
cluster. ConfigMaps provide a way to manage
configuration data, making it easier to update the
configuration of an application without having to
rebuild and redeploy the application.

why we use helm and advantages
**Helm** is a **package manager for Kubernetes** — like `apt` or `yum`, but for k8s apps.
It packages Kubernetes manifests into reusable units called **Charts**.

**Why we use Helm:**

* To **deploy complex applications easily** (like Jenkins, Prometheus, etc.)
* To **manage versions, upgrades, and rollbacks** of deployments
* To **parameterize** manifests using **values.yaml** (no manual editing)
* To **reuse** and **share** applications across environments

**Advantages:**
✅ Simplifies deployment and updates
✅ Reusable and consistent configurations
✅ Easy rollback to previous versions
✅ Reduces YAML complexity

👉 In short: **Helm = easy, versioned, and repeatable app deployment for Kubernetes.**


node selector [ node labels ]
**Node Selector** is the **simplest way to schedule pods** on specific nodes using **node labels**.

**Steps:**

1. **Label a node:**

   ```bash
   kubectl label node node1 env=prod
   ```

2. **Add nodeSelector in Pod/Deployment:**

   ```yaml
   spec:
     nodeSelector:
       env: prod
   ```

👉 In short:
**Node labels** = tags on nodes
**NodeSelector** = tells the pod to run only on nodes with matching labels.



What are Labels and Selectors in Kubernetes?
**Labels** – are **key-value pairs** attached to Kubernetes objects (like pods, nodes, services) to **identify and group them**.
👉 Example:

```yaml
labels:
  app: frontend
  env: prod
```

**Selectors** – are **queries** used to **filter or match objects** based on labels.
👉 Example:

```yaml
selector:
  matchLabels:
    app: frontend
```

**In short:**

* **Labels** = tags that describe objects
* **Selectors** = filters that find those objects (e.g., Deployments → Pods).

What is a label in Kubernetes and how is it used?

A label in Kubernetes is a key-value pair attached to
resources such as pods, services, and nodes. Labels are
used to identify and group resources and to provide
metadata about the resources. Labels can be used to
select a group of resources and perform operations on
them, such as scaling or rolling updates.



What is the difference between a StatefulSet and a Deployment in Kubernetes?
**StatefulSet vs Deployment — key differences:**

| Feature          | **Deployment**                     | **StatefulSet**                                             |
| ---------------- | ---------------------------------- | ----------------------------------------------------------- |
| **Use case**     | Stateless apps (e.g., web servers) | Stateful apps (e.g., databases)                             |
| **Pod identity** | Pods are identical                 | Each pod has a unique, stable name (e.g., `pod-0`, `pod-1`) |
| **Storage**      | Uses shared or ephemeral storage   | Each pod gets its own **persistent volume**                 |
| **Scaling**      | Any pod can replace another        | Orderly scaling (start/stop in sequence)                    |
| **Network ID**   | Random pod names                   | Fixed DNS names for each pod                                |

👉 In short:
**Deployment = stateless & interchangeable pods**
**StatefulSet = stateful, ordered, and persistent pods**


OIDC
**OIDC (OpenID Connect)** is an **identity layer built on top of OAuth 2.0** — it’s used for **authentication** (verifying *who* you are).

In **Kubernetes**, OIDC is used mainly for:

* **Integrating external identity providers** (like AWS IAM, Google, Okta, Azure AD).
* **Enabling IRSA (IAM Role for Service Account)** in EKS — so pods can securely assume IAM roles **without storing AWS credentials**.

👉 In short:
**OIDC = secure authentication via external identity provider** — commonly used in EKS for **IRSA and federated access**.

ServiceAccount

**ServiceAccount** in Kubernetes is an **identity used by pods** to interact securely with the Kubernetes API or other services.

**Key points:**

* Each pod automatically gets a **default ServiceAccount** (unless specified).
* You can **create custom ServiceAccounts** and attach them to pods for specific permissions.
* Works with **RBAC** to control what the pod can do.
* In **EKS**, combined with **OIDC + IRSA** to access AWS resources securely.

**Example:**

```bash
kubectl create serviceaccount my-sa
```

Then in a pod:

```yaml
serviceAccountName: my-sa
```

👉 In short:
**ServiceAccount = identity for pods** (like a “user” for applications inside Kubernetes).


**Liveness Probe** → checks if the **container is still running properly**.

* If it fails → Kubernetes **restarts the container**.
  👉 Example: Detects app crash or deadlock.

**Readiness Probe** → checks if the **container is ready to receive traffic**.

* If it fails → pod is **removed from Service endpoints** (no traffic sent).
  👉 Example: App still starting up or not yet ready.

**In short:**

* **Liveness = should I restart it?**
* **Readiness = should I send traffic to it?**
